# Database

Briefbot uses SQLite as the primary archive and dashboard state store.

Default path:

```text
data/briefbot.db
```

The database is initialized by `briefbot.store.Store` and augmented by `dashboard.backend.dao.BriefbotDAO`. SQLite WAL mode is enabled by the core schema.

## Connecting From Another App

An external app can connect directly to the SQLite file or call the dashboard HTTP API.

Prefer the HTTP API when:

- the other app runs on another host or container
- you want stable JSON response shapes
- you want the same query behavior as the dashboard
- you want `/ask` query history to be recorded

Direct SQLite reads are useful when:

- the other app runs on the same host
- it only needs archive reads or analytical queries
- it can tolerate schema-level coupling

For direct reads, open the DB read-only and set a busy timeout:

```python
import sqlite3

db_path = "/Users/bubz/Developer/agent/projects/ai-assistant/data/briefbot.db"
conn = sqlite3.connect(f"file:{db_path}?mode=ro", uri=True, timeout=30)
conn.row_factory = sqlite3.Row
conn.execute("PRAGMA busy_timeout = 5000")

rows = conn.execute("""
    SELECT item_id, title, url, source_name, published_at, score
    FROM items
    ORDER BY datetime(COALESCE(published_at, fetched_at)) DESC
    LIMIT 20
""").fetchall()
```

Do not write to core tables from another process unless you adopt Briefbot's schema and dedupe rules. If another app needs to store its own state, create app-prefixed tables or use a separate database.

## Core Tables

### `items`

Long-lived item archive. Important columns:

- `item_id`: stable primary key.
- `dedupe_key`: unique key for dedupe.
- `canonical_url`, `url`: link fields.
- `source_id`, `source_name`, `source_category`, `source_tier`: source metadata.
- `title`, `author`, `summary`: display/search text.
- `published_at`, `fetched_at`, `last_seen_at`: ISO timestamps.
- `tags_json`: JSON array of tags.
- `watch_hits_json`: JSON array of watchlist hits.
- `raw_json`: normalized raw source payload.
- `metrics_json`: source-specific metrics.
- `score`: general ranking score.
- `score_opportunity`, `opportunity_reason`, `opportunity_tags_json`: opportunity lens.

Useful item query:

```sql
SELECT item_id, title, url, source_name, published_at, score, tags_json
FROM items
WHERE datetime(COALESCE(published_at, fetched_at)) >= datetime('now', '-7 days')
ORDER BY score DESC
LIMIT 25;
```

### `clusters`

Storyline clusters generated by the radar layer.

Important columns:

- `cluster_id`: primary key.
- `label`: generated cluster label.
- `first_seen_at`, `last_seen_at`: cluster activity window.
- `item_count`, `sources_count`: breadth.
- `velocity_1d`, `velocity_3d`, `velocity_7d`: recent activity.
- `diversity_score`, `trend_score`: ranking signals.
- `representative_title`, `representative_url`: display representative.

### `cluster_memberships`

Maps items to clusters:

- `item_id`
- `cluster_id`
- `assigned_at`
- `similarity`

Join pattern:

```sql
SELECT c.label, c.trend_score, i.title, i.url, i.source_name
FROM cluster_memberships m
JOIN clusters c ON c.cluster_id = m.cluster_id
JOIN items i ON i.item_id = m.item_id
WHERE c.cluster_id = ?
ORDER BY i.score DESC;
```

### `cluster_events`

Daily cluster activity:

- `cluster_id`
- `date`
- `items_added`
- `sources_added`
- `top_item_id`

### `topic_profiles`

Rolling topic statistics:

- `topic_id`
- `name`
- `kind`
- `count_1d`, `count_3d`, `count_7d`, `count_30d`
- `momentum`
- `first_seen_at`, `last_seen_at`

### `summaries`

Cached item/article summaries:

- `item_id`
- `provider`
- `model`
- `summary_md`
- `content_hash`
- `created_at`, `updated_at`

Primary key is `(item_id, provider, model)`.

### `exec_summary_cache`

Stage-1 JSON summaries for daily executive brief generation:

- `cache_key`
- `url`
- `excerpt_hash`
- `excerpt_text`
- `stage1_json`
- `provider`
- `model`
- `created_at`, `updated_at`

This cache lets the daily brief reuse article-level extraction/summarization.

### `discovered_feeds` and `feed_cache`

Fetcher support tables:

- `discovered_feeds`: site URL to discovered feeds cache.
- `feed_cache`: ETag/Last-Modified cache for feeds.

## Dashboard Tables

These are created by `BriefbotDAO`:

### `dashboard_queries`

Ask page history:

- `id`
- `created_at`
- `user_query`
- `llm_response_md`
- `tool_name`
- `tool_args_json`
- `tool_result_json`
- `error`
- `llm_provider`
- `llm_model`

The dashboard keeps recent query history to 14 days and 20 entries by default.

### `dashboard_story_feedback`

Current feedback state by item:

- `item_id`
- `vote`: `-1`, `0`, or `1`
- `score`
- `updated_at`

### `dashboard_story_feedback_events`

Append-only feedback events:

- `id`
- `item_id`
- `section`
- `signal`
- `source_name`
- `cluster_id`
- `tags_json`
- `created_at`

### `dashboard_favorite_folders` and `dashboard_favorite_links`

Favorite link storage used by the dashboard.

## JSON Columns

Several columns store JSON arrays or objects as text:

- `items.tags_json`
- `items.watch_hits_json`
- `items.raw_json`
- `items.metrics_json`
- `items.opportunity_tags_json`
- `dashboard_queries.tool_args_json`
- `dashboard_queries.tool_result_json`

SQLite JSON1 functions are used in the dashboard DAO. Example:

```sql
SELECT lower(trim(json_each.value)) AS tag, COUNT(*) AS count
FROM items, json_each(items.tags_json)
GROUP BY lower(trim(json_each.value))
ORDER BY count DESC;
```

## Recommended Integration Queries

Latest high-score stories:

```sql
SELECT item_id, title, url, source_name, published_at, score, summary
FROM items
WHERE datetime(COALESCE(published_at, fetched_at)) >= datetime('now', '-3 days')
ORDER BY score DESC
LIMIT 20;
```

Recent trending clusters:

```sql
SELECT cluster_id, label, trend_score, velocity_7d, representative_title, representative_url
FROM clusters
WHERE datetime(COALESCE(last_seen_at, created_at)) >= datetime('now', '-14 days')
ORDER BY trend_score DESC
LIMIT 20;
```

Items for a cluster:

```sql
SELECT i.item_id, i.title, i.url, i.source_name, i.published_at, i.score
FROM cluster_memberships m
JOIN items i ON i.item_id = m.item_id
WHERE m.cluster_id = ?
ORDER BY i.score DESC
LIMIT 25;
```

Ask history:

```sql
SELECT id, created_at, user_query, llm_response_md, tool_name, tool_args_json
FROM dashboard_queries
ORDER BY datetime(created_at) DESC
LIMIT 20;
```

## Concurrency Notes

Briefbot and the dashboard may write while another app reads. Because WAL mode is enabled, read-only connections can usually read concurrently. Use read-only mode for external analytics and set `busy_timeout` to avoid immediate failures during brief write transactions.

Avoid long write transactions from other apps. If an agent harness needs durable integration state, either:

- write to its own database, keyed by Briefbot `item_id` or `cluster_id`; or
- create separate harness-owned tables with a clear prefix such as `agent_harness_*`.
